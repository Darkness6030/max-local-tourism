# MAX.Локальный Туризм

Мини-приложение для поездок выходного дня. Рабочее название интерфейса — «Рядом»: пользователь задаёт город, даты, бюджет и интересы, получает программу с погодой, транспортом, картой и текстом для обсуждения со спутниками в MAX.

Рабочий адрес miniapp: **https://kaktut.ru/max/app**. Развёртывание на сервере **Dental** изолировано от остальных приложений. Организаторы зарегистрировали этот адрес у бота. Операционные команды и откат: [deploy/README.md](deploy/README.md). В обычном браузере production предлагает открыть MAX; гостевой обход отключён.

## Что реализовано

- React + TypeScript + Vite + Tailwind CSS: мобильный интерфейс «Рядом», авторская иллюстрация, локальные шрифты Manrope, иконки Lucide и анимации Motion. Поддержка `prefers-reduced-motion` и безопасных отступов экрана.
- Онбординг из трёх экранов со свайпами, главная с выбором настроения, анкета из пяти шагов: направление → даты → компания → интересы → детали. Восстановление черновика и шага в текущей вкладке.
- Экран генерации с реальным прогрессом, восстановлением задачи и повтором проверки статуса. Маршрут с вкладками программы/дороги/бюджета, погодой, списком вещей, картой, копированием и шерингом. Разделы «Мои поездки» и «О сервисе».
- MAX Bridge: `ready`, BackButton, подтверждение закрытия, внешние ссылки и текстовый `shareMaxContent` по нажатию. В браузере — `max.ru/:share` и копирование. Сообщения автоматически не отправляются.
- Backend-проверка подписи `initData`, срока действия и дубликатов; владение задачами и поездками. Локальный режим явно включается и запрещён в production.
- Провайдеры: GigaChat, Nominatim/geopy, Open-Meteo или OpenWeather, Яндекс Расписания. Карта общественного транспорта использует координаты фактических станций.
- Профиль MAX: имя, фамилия, ник и фото из подписанных данных запуска после серверной проверки. При отсутствии фотографии показываются инициалы. Персональные маршруты создаются по реальным запросам. Отдельная подборка готовых маршрутов — Коломна, Суздаль, Выборг и Великий Новгород — открывается сразу и позволяет заполнить анкету по выбранному направлению. На главной показываются только направления из выбранного города: Москва — Коломна и Суздаль; Санкт-Петербург — Выборг и Великий Новгород. Смена города сохраняет анкету, плавно обновляет главную с тем же переходом, что у вкладок, и меняет обложку без перезагрузки документа. Авторство фотографий доступно в «О сервисе». Программы не содержат имитации погоды и расписаний.
- Docker с отдельным этапом сборки Vite, healthcheck, непривилегированный пользователь, lock-файлы зависимостей и закреплённые базовые образы. В runtime работает только Python; FastAPI раздаёт собранный frontend.

## Быстрый локальный запуск

Нужны Docker Engine/Desktop и Docker Compose v2.24+. Все локальные компоненты запускаются одной командой:

```bash
docker compose up --build -d
```

Открыть **http://127.0.0.1:8000/**. Для генерации нужны внешние ключи в `.env`; при отсутствии доступа к сервису показывается ошибка. Порт опубликован только на `127.0.0.1`.

Если 8000 занят:

```bash
APP_PORT=8001 docker compose up --build -d
```

Тогда приложение доступно на **http://127.0.0.1:8001/**. В текущем workspace используется 8001, чтобы не останавливать сервис на 8000.

Существующий `.env` не перезаписывать. В новом окружении скопировать `.env.example` в `.env` и заполнить необходимые поля. После изменения настроек выполнить `docker compose up -d --force-recreate` с тем же `APP_PORT`, если он менялся.

Остановка и повторный запуск:

```bash
docker compose down
APP_PORT=8001 docker compose up -d
```

Для стандартного порта `APP_PORT=8001` не нужен. **Поездки и задачи хранятся в PostgreSQL, в Docker volume `postgres_data`.** Обычные перезапуски и `docker compose down` сохраняют данные; `down -v` удаляет volume. `./data` содержит CA-файлы и подключён только для чтения.

`compose.yaml` предназначен только для локальной разработки. Он включает development-авторизацию и разрешает точные адреса Docker gateway (`172.30.0.1`) и хост-прокси Docker Desktop, сохраняя проверки loopback Host/Origin. При конфликте подсети адаптировать subnet/gateway и `MAX_LOCAL_CLIENT_HOSTS` вместе. Не использовать этот compose как production-конфигурацию.

## Разработка frontend

Нужны Node.js 22.12+ и работающий backend (по умолчанию `http://127.0.0.1:8001`). Из корня:

```bash
npm ci --prefix frontend
npm run dev --prefix frontend
```

Открыть **http://127.0.0.1:5173/**. Vite обновляет интерфейс при изменениях и проксирует `/api` на backend. Для другого порта: `BACKEND_URL=http://127.0.0.1:8000 npm run dev --prefix frontend`. Корневой `.env` не загружается в Vite: токены остаются на backend.

```bash
npm run typecheck --prefix frontend
npm run build --prefix frontend
```

Стили компонентов задаются утилитами Tailwind CSS 4 в JSX; повторяющиеся наборы находятся в `frontend/src/ui-styles.ts`. `data-ui` служит стабильным селектором для состояний, вложенных элементов и браузерных проверок. В `styles.css` оставлены глобальные настройки, исходный reset, анимации и адаптивные варианты. Preflight не подключён, чтобы сохранить прежнее оформление элементов браузера. Именованные варианты сохраняют исходные границы экранов и порядок переопределений; при изменениях проверять также узкие и низкие окна.

Сборка создаёт `src/static/`, очищая предыдущую сборку. Это генерируемый каталог, исходники находятся в `frontend/src/`. Docker собирает его автоматически через `npm ci`; Node-сервер для собранного приложения не нужен. Подробности иллюстрации и исходный промпт: [frontend/ASSETS.md](frontend/ASSETS.md).

## Python без Docker

Проверяемое окружение — Python 3.12; используются возможности Python 3.11+.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm ci --prefix frontend
npm run build --prefix frontend
python main.py
```

В `.env` установить `MAX_ALLOW_LOCAL_AUTH=true` и `DATABASE_URL` для доступной PostgreSQL. Compose не публикует порт БД; для Python на хосте нужна отдельная локальная БД или явная публикация её порта только на loopback. Начальная схема создаётся при старте; будущие изменения структуры требуют отдельной миграции. `main.py` слушает `127.0.0.1:8000`, не доверяет proxy headers и включает reload. Для другого порта:

```bash
python -m uvicorn main:app --host 127.0.0.1 --port 8001 --no-proxy-headers
```

Внешние сервисы требуют интернет, разрешения и квоты; их нельзя воспроизвести внутри Docker. Open-Meteo и Nominatim в текущем режиме не требуют ключей. GigaChat и Яндекс Расписания требуют действующих доступов; README и пример окружения их не содержат. Health показывает наличие настройки, а не успешность запросов.

`requirements.txt` задаёт прямые зависимости, `requirements.lock` фиксирует транзитивные. Для асинхронного геокодинга необходим **geopy[aiohttp]**. Проверочная чистая Docker-сборка после загрузки базового образа заняла менее минуты; требование конкурса — не более пяти минут.

## MAX: сертификат и проверка токена

API: `https://platform-api2.max.ru`, токен — в заголовке Authorization. Для API требуется доверие CA Минцифры. Скрипт скачивает официальный сертификат Госуслуг по HTTPS только в проект, не меняя системное доверие:

```bash
python scripts/setup_max_ca.py
```

После этого в `.env`:

```dotenv
MAX_CA_BUNDLE_FILE=data/certs/russian-trusted-root.pem
GIGACHAT_CA_BUNDLE_FILE=data/certs/russian-trusted-root.pem
GIGACHAT_VERIFY_SSL_CERTS=true
```

Справка: [сертификаты Госуслуг](https://www.gosuslugi.ru/crt). В Docker файл доступен через read-only mount `./data`. Для другого CA можно указать свой PEM bundle. Не отключать TLS-проверку ради обхода ошибки сертификата.

Read-only проверка бота, без сообщений и изменения настроек:

```bash
python -m src.services.max_bot
# Или в контейнере:
docker compose exec app python -m src.services.max_bot
```

Скрипт выводит только ID, username, имя и флаг бота. Токен хранится в локальном `.env`, исключённом из Git и Docker-образа.

В MAX frontend передаёт raw `window.WebApp.initData` в `X-Max-Init-Data`. Backend проверяет HMAC-SHA256, срок и user.id. Неверная подпись не превращается в локального гостя. Чужой ID поездки/задачи даёт 404, отсутствие авторизации — 401. UI не сохраняет initData в браузерное хранилище.

## Проверка пользовательского сценария

1. Открыть miniapp через бота MAX. Пройти знакомство; в «О сервисе» проверить имя, фамилию, ник и фото своего профиля.
2. Нажать «Спланировать поездку» и пройти пять шагов: направление, даты, компания, интересы, бюджет и транспорт.
3. Нажать «Собрать мою поездку», дождаться программы, погоды, дороги и бюджета. Ошибки провайдеров показываются явно, ответы анкеты сохраняются.
4. Проверить вкладки маршрута, карту, копирование и шеринг. Выбор чата и отправка остаются за пользователем.
5. В обычном браузере production должен предлагать открыть MAX. Без подписи API возвращает 401; чужая поездка — 404.

На Dental выполнен реальный запрос Москва → Коломна: Open-Meteo, транспорт и ИИ, около 60 секунд. HTTPS, загрузка ресурсов, подпись, изоляция и отображение профиля проверены с синтетически подписанными тестовыми данными. Это проверка технического пути, а не вход реального пользователя через клиент MAX. Авторизацию на конкретном устройстве подтверждает открытие miniapp из MAX.

## API

В production пользовательские endpoints требуют `X-Max-Init-Data`. Публичны только страница, ресурсы, health и UI-конфигурация. Диагностические маршруты, Swagger и OpenAPI доступны только при локальной разработке. OpenAPI 3.1: `/openapi.json`, Swagger: `/docs` (Authorize → MaxInitData). Снимок схемы в корне обновляется командой `python scripts/export_openapi.py`.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/v1/health` | Версия/настройки без секретов |
| GET | `/api/v1/app-config` | Горизонт дат и параметры формы |
| GET | `/api/v1/auth/me` | Проверенный пользователь и режим |
| GET | `/api/v1/examples/trip-request` | Анкета с будущей датой |
| POST | `/api/v1/trips/jobs` | 202: ID и URL статуса |
| GET | `/api/v1/trips/jobs/{id}` | Прогресс/итог/ошибка своей задачи |
| POST | `/api/v1/trips/generate` | Ожидание той же фоновой генерации с общими лимитами |
| GET | `/api/v1/trips/{id}` | Свой маршрут |
| GET | `/api/v1/trips/{id}/share` | Текст для шеринга |
| GET | `/api/v1/geocode`, `/weather`, `/transport` | Диагностика провайдеров |
| POST | `/api/v1/destinations/suggest` | AI-подбор направления |

`/demo` — старая техническая JSON-форма, только в development/test. Основной интерфейс — `/`. Локальные read-only проверки:

```bash
curl -fsS http://127.0.0.1:8001/api/v1/auth/me
curl -fsS http://127.0.0.1:8001/api/v1/examples/trip-plan
```

Для генерации отправить JSON из `/examples/trip-request` на POST `/trips/jobs` и опрашивать status_url. История: `GET /trips?limit=20&cursor=<id>` (cursor необязателен), в ответе `items`, `total`, `next_cursor`. Доступ только к своим поездкам. Состояния: queued → running → succeeded/failed. Повторная активная генерация пользователя/превышение ёмкости — 429, невалидная анкета — 422.

## Архитектура, данные и ограничения

```text
MAX / браузер → React (сборка Vite) + Bridge → FastAPI + проверка initData
 → TripJobManager → TripPlanner → геокодер + погода + расписания + GigaChat
 → TripStore → PostgreSQL (поездки, задачи, владелец) → карточки + пользовательский шеринг
```

`src/auth.py` — идентификация; `src/api/` — HTTP; `src/services/` — провайдеры и planner; `src/jobs.py`/`store.py` — задачи и результаты; `frontend/src/` — UI; `src/static/` — результат сборки; `src/sample.py` — фикстура автоматических тестов, недоступная через production API. Один процесс, один worker. Healthcheck проверяет процесс, а не все провайдеры.

- Старт: Москва и Санкт-Петербург, 1–3 дня. Open-Meteo: 16 дней; OpenWeather: UI ограничен пятью днями. Backend проверяет доступность прогноза у провайдера.
- Готовая поездка и успешный статус задачи записываются одной транзакцией в PostgreSQL. История с пагинацией доступна в «Мои поездки» для текущего пользователя MAX и не зависит от браузерного хранилища. При перезапуске незавершённые генерации помечаются как прерванные; готовые маршруты сохраняются. Один worker на БД защищён advisory lock. Автоматического удаления поездок пока нет.
- sessionStorage хранит черновик, шаг и ID результата/задачи по пользователю в текущей вкладке. localStorage содержит только факт прохождения онбординга. Профиль и MAX launch data в хранилища не пишутся.
- GigaChat получает анкету и факты API без профиля MAX. Программа и расходы — рекомендации/оценки. Возможны временные несоответствия; строгая проверка всего таймлайна относительно рейсов пока не завершена. AI-текст не подтверждает часы работы и время транспорта.
- Прогноз/расписание актуальны на момент запроса. Координаты станций берутся из API; при отсутствии карта может быть недоступна. Ссылка на расписание не покупает и не бронирует билет.
- Ошибка расписания допускает результат с предупреждением; ошибка погоды прекращает генерацию. Демо не подменяет провайдеров. Автомобильный сценарий не учитывает пробки.
- Nominatim: один запрос в секунду в процессе, кэш локальный. Для роста нужны квоты/свой геокодер. Для LLM пока нет суточного бюджета расхода; диагностические endpoints в production отключены.
- DATA-API.yaml по шаблону организаторов и конкурсная презентация ещё впереди. Каталог исходно не содержит Git-истории; фиксация конкурсной версии не выполнена.

## Тесты

```bash
npm run build --prefix frontend
TEST_DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/TEST_DB pytest -q
```

Тесты хранилища требуют отдельную PostgreSQL через `TEST_DATABASE_URL`; без неё они пропускаются. Каждый тест создаёт и удаляет только собственную случайную схему. Никогда не указывайте рабочую БД. Проверяются восстановление после переподключения, атомарность, пагинация и разделение владельцев. Unit/API-тесты не вызывают внешние сервисы: planner/провайдеры, подпись/подмена/TTL, локальный обход, изоляция, лимиты, static UI и пользовательский профиль. Проверка на зависимостях контейнера:

```bash
docker compose run --rm -e TEST_DATABASE_URL=postgresql://tourism:local-tourism@db:5432/tourism -v "$PWD/tests:/app/tests:ro" app python -m pytest -q -p no:cacheprovider
```

Браузерная проверка требует Chrome и dev-зависимостей:

```bash
pip install -r requirements-dev.txt
python scripts/check_ui.py --base-url http://127.0.0.1:8001
python scripts/check_ui.py --base-url http://127.0.0.1:8001 --height 633
python scripts/check_presets.py --base-url http://127.0.0.1:8001
python scripts/check_compact_ui.py --base-url http://127.0.0.1:8001
ruff check src tests scripts
```

Без Chrome: установить `python -m playwright install chromium`, передать `--browser chromium`. Скрипт проверяет экраны 320/390/1360 px, онбординг, все пять шагов, черновик, валидацию, ошибки, повтор polling без новой генерации, вкладки, безопасный текст и эмулированный Bridge. Реальная генерация/отправка сообщений не выполняются. Скриншоты — `tmp/ui-check/`, вне Git.

## Рабочая среда MAX

На Dental используется `deploy/compose.production.yaml`: APP_ENV=production, MAX_ALLOW_LOCAL_AUTH=false, TLS-проверка внешних API и сертификат только внутри приложения. Nginx проксирует `/max/app` и `/max/app/` на `127.0.0.1:18091`; остальные маршруты домена сохранены. Ресурсы Vite собираются с этим префиксом, API получает правильный ASGI root_path.

Профиль приходит через `WebApp.initData`, а при необходимости — из `WebAppData` в URL-фрагменте. `initDataUnsafe` для доверия профилю не используется. На backend проверяются HMAC, срок и дубликаты параметров, затем frontend получает разрешённые поля через `/auth/me`. Секрет бота остаётся на сервере. [Документация MAX по валидации](https://dev.max.ru/docs/webapps/validation), [поля профиля Bridge](https://dev.max.ru/docs/webapps/bridge).

```bash
python scripts/check_production.py
# Один реальный запрос к внешним сервисам, с расходом их квот:
python scripts/check_production.py --generate
```

Проверка использует синтетически подписанный служебный профиль и не отправляет сообщений. Имя, ник и логотип бота не менялись.

Внутренние `docs/PLAN.md`, `docs/RULES.md` и PDF задания исключены из Git из-за ограничений распространения задания; они остаются в workspace. `docs/PROGRESS.md` пустой по указанию владельца.

## Приветствие в боте

При начале общения (`bot_started`) и команде `/start` в личном диалоге бот отправляет приветствие и кнопку **«Открыть Рядом»** типа `open_app`. Кнопка открывает мини-приложение бота из `MAX_BOT_USERNAME`. Обычные сообщения и групповые чаты не вызывают ответ.

Обработчик `POST /api/v1/bot/webhook` включается только при заданных `MAX_WEBHOOK_SECRET`, `MAX_BOT_TOKEN` и `MAX_BOT_USERNAME`. Секрет проверяется по заголовку `X-Max-Bot-Api-Secret`; хранить его только в серверном `.env`. Подписка создаётся явно:

```bash
python scripts/register_bot_webhook.py --url https://kaktut.ru/max/app/api/v1/bot/webhook
```

Скрипт проверяет существующие подписки, не удаляет их и не меняет имя, настройки miniapp или команды бота. Обработчик приветствия не обращается к БД: проверяет событие и отправляет ответ через SDK. При ошибке отправки возвращается 503 для повторной доставки MAX. Повторная доставка одного события может повторить приветствие — отдельного хранения обработанных событий нет. Старая таблица `bot_deliveries` больше не используется; удалять её для обновления не требуется.

Контракты: [Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions), [кнопки MAX](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard).

## Проверка города и фото направления

В ручном выборе кнопка «Продолжить» проверяет город через защищённый `GET /api/v1/cities/validate?origin=...&destination=...`. Допускаются существующие города России, строго ближе 600 км **по прямой** от выбранной точки отправления; тот же город отклоняется. Если название неоднозначно, можно дописать область через запятую. Сервер повторяет проверку перед созданием задачи и при генерации, включая направления ИИ. Граница сравнивается до округления расстояния.

Nominatim вызывается только по явному действию, без автодополнения: один запрос в секунду на приложение, последовательные обращения и ограниченный кэш. Город проверяется по типу объекта и полному названию/известным псевдонимам, области и отдельные достопримечательности не принимаются. Сервер провайдера задаётся через `NOMINATIM_DOMAIN`. [Политика Nominatim](https://operations.osmfoundation.org/policies/nominatim/).

Новые маршруты получают необязательное `destination_photo`: основное свободное фото соответствующей статьи русской Википедии, проверенной по координатам города. Поиск использует OSM-ссылку на статью либо геопоиск Wikipedia; Wikimedia Commons предоставляет автора и лицензию. Фото с атрибуцией сохраняется вместе с поездкой в JSON PostgreSQL без изменения схемы таблиц. Старые поездки без фото остаются читаемыми. Если источник недоступен или подходящего свободного изображения нет, маршрут показывается без обложки. Изображения не подменяются фотографиями других городов.


### Бюджет и гостиницы

Новые расчёты содержат явный запас **25%** поверх базовых расходов. Модель больше не обязана искусственно укладывать оценку в лимит: превышение видно в бюджете. Значения цен из транспортного API сохраняются без изменений. Стоимость активностей показана до резерва; резерв учитывается один раз в итоговой сумме. Исторические оценки уже сохранённых поездок не пересчитываются.

Для новых поездок на 2–3 дня backend получает гостиницы и гостевые дома через бесплатный [Overpass API VK Maps](https://maps.mail.ru/osm/tools/overpass/), без ключа и регистрации. [Публичные инстансы и условия](https://wiki.openstreetmap.org/wiki/Overpass_API#Public_Overpass_API_instances). Это каталог OpenStreetMap, **не API бронирования**: нет актуальных тарифов, свободных номеров или гарантии полноты. В программе показаны до пяти ближайших мест в радиусе 8 км от точки города, адрес при наличии, ссылка на карту и сайт из OSM. Атрибуция: [© OpenStreetMap contributors, ODbL](https://www.openstreetmap.org/copyright).

Оценка проживания — ориентир модели для одного двухместного номера за ночь на даты поездки; если она отсутствует, используется явно обозначенное планировочное допущение 5 000 ₽. Число номеров = округлённое вверх `travelers / 2`, число ночей = `days - 1`. Детское размещение нужно уточнять у гостиницы. Оценка не приписывается конкретному отелю. Проживание добавляется один раз к бюджету до общего резерва 25%.

`OVERPASS_API_URL` позволяет сменить поставщика без изменения кода. Запросы выполняются только backend, последовательно, с общим пределом 40 секунд, радиусом и объёмом ответа, ограниченными в запросе. Каталог города кэшируется на 24 часа (до 256 городов); после сбоя — пауза 5 минут для всего провайдера, без повторных запросов в цикле. Сбой или пустой каталог не ломает поездку: видны пояснение и поиск гостиниц на карте. Для роста нагрузки нужен собственный инстанс или согласованный тариф — публичный API не имеет SLA. Каталог и момент получения сохраняются в JSONB вместе с поездкой; старые записи без поля `accommodation` продолжают открываться.

Проверки: `pytest` покрывает расчёты, 1/2/3 дня, число номеров, превышение лимита, дедупликацию и географию отелей, недоступный/пустой API, кэш, перезагрузку из PostgreSQL и владельцев. `python scripts/check_hotels_ui.py --base-url http://127.0.0.1:18092` проверяет новый блок на 320/390/1360 px и его отсутствие в однодневных/старых результатах, без реальных внешних запросов.

Рефакторинг: общие бизнес-константы, расчёт расстояния в `src/routing.py`, бюджет в `src/services/budget.py`, общие Tailwind-рецепты в `frontend/src/ui-styles.ts`, единый список вкладок результата. Удалены неиспользуемый параметр `Brand.compact` и зависимости Alembic/Mako/MarkupSafe: миграций Alembic в проекте нет, текущая инициализация SQLModel остаётся прежней. Локальные пользовательские материалы и инструменты разработки не удаляются.

### SDK MAX

Bot API подключён через [max-messenger/max-botapi-python](https://github.com/max-messenger/max-botapi-python), закреплён коммит `4a286baa06d38f2db9f7244d94f89508743f8fee` (`maxapi` 0.9.4). Это проверенный командой MAX форк; пакет PyPI `maxapi` не подменяет указанный репозиторий. SDK используется для `get_me`, `send_message`, подписок webhook, моделей входящих `BotStarted`/`MessageCreated` и кнопки `OpenAppButton`. Существующий FastAPI webhook сохраняет проверку секрета и не зависит от БД; polling и автоматическая перерегистрация подписок не запускаются.

В закреплённой версии SDK устарели значения подключения по умолчанию. `src/services/max_bot.py` задаёт текущий `https://platform-api2.max.ru`, убирает `access_token` из query, передаёт токен только в `Authorization`, сохраняет TLS с дополнительным CA, запрещает редиректы, убирает необязательные null из payload и не пропускает сырой текст ошибки провайдера в логи SDK. Общий лимит операции 18 с, HTTP-запроса 15 с; сессия всегда закрывается. Проверка подписи miniapp initData и браузерный MAX Bridge остаются отдельными контрактами — Python Bot API SDK их не заменяет.

`python -m src.services.max_bot` — реальная read-only проверка SDK. Автотесты отправки сообщений и регистрации подписок используют только локальный mock API; проверяют заголовки, отсутствие токенов в URL, payload кнопки, редиректы, ошибки и защиту чужой подписки. В текущем SDK есть предупреждения Pydantic о старом формате Config; Pydantic 2 закреплён, переход на 3 требует обновления SDK.

## Чеклист сохранённой поездки

Галочки переключаются мгновенно, запросы сохранения выполняются последовательно в фоне. Новые клики сохраняют приоритет над запоздавшими ответами; при ошибке несохранённые отметки откатываются с пояснением. Отметки «Не забудьте взять» сохраняются в JSONB поездки (`packed_items`, индексы пунктов), доступны только владельцу и восстанавливаются после перезапуска. `PATCH /api/v1/trips/{trip_id}/packing` принимает `item_index` и `checked`; обновление одного пункта выполняется под блокировкой строки, без потери параллельных отметок. Старые записи без отметок открываются с пустым чеклистом, миграция таблиц не требуется.

При сохранении любых изменений содержимого поездки `TripStore.put` сбрасывает отметки; повторная запись неизменного плана сохраняет их. Перегенерация создаёт отдельную поездку с пустым чеклистом, прежняя запись в истории остаётся самостоятельной поездкой. Чеклисты редакционных примеров не относятся к сохранённым персональным поездкам.

Браузерная проверка сохранения, повторного открытия и ошибки запроса: `.venv/bin/python scripts/check_packing_ui.py --base-url http://127.0.0.1:18092` (API замокан). Тесты `tests/test_packing.py` проверяют хранение в реальной изолированной PostgreSQL, владельца, параллельные отметки и сброс после изменений.

## Разнообразие направлений

Автоподбор запрашивает у GigaChat до пяти разных городов с объяснением соответствия анкете и внутренней оценкой 0–100. Главный интерес, длительность, автомобиль, бюджет на человека, состав группы, темп и сезон важнее популярности. Для узкого запроса допустим один кандидат. Температура подбора — 0.7; программа поездки остаётся на 0.2. Это один запрос к модели на подбор, не пять.

`src/services/destinations.py` содержит 48 ориентиров для Москвы и 25 для Петербурга. Порядок перемешивается; список открыт для других реальных городов. Подбор ориентиров сверялся с [маршрутами туристического портала Московской области](https://welcome.mosreg.ru/routes/ekskursionnye-marsruty), [порталом Калужской области](https://visit-kaluga.ru/disticts/tarusa/), [туристическим сайтом Торжка](https://visit-torzhok.ru/) и [Музейным агентством Ленинградской области](https://www.lenoblmus.ru/ekskursii?page=1). Это подсказки для поиска, не база проверенных расписаний, цен или достопримечательностей.

Backend выбирает случайный вариант среди кандидатов, отстающих от лучшей оценки не более чем на 10 баллов. В этой группе сначала рассматриваются города, отсутствующие в последних восьми сохранённых поездках владельца. Если подходящие города уже встречались, повтор разрешён; явно лучший ответ на узкое пожелание сохраняет приоритет. Оценки — суждение модели, а не объективный рейтинг, пользователю они не показываются. Причина выбора относится именно к выбранному городу.

История читается одним запросом PostgreSQL только при автоматическом подборе; в модель передаются названия городов, без MAX-профиля и чужих поездок. Ручной выбор города не меняется. Выбранное направление по-прежнему проходит геокодирование и проверку расстояния, после чего отдельно загружаются погода, транспорт, фото и гостиницы. Проверки выбора, недавних поездок и изоляции владельцев: `tests/test_destinations.py`.
